# EP.08 CI/CD 流水线

> 对应正文：[docs/08-cicd.md](../docs/08-cicd.md)（覆盖 CICD-B1 CI 与 CD 辨析 / CICD-I1 完整 CI 流水线 / CICD-I2 蓝绿与金丝雀 / CICD-A1 云原生构建 / CICD-A2 多环境流水线）· 配套示例：`../examples/08-cicd/workflows/i1-full-ci.yml`、`../examples/08-cicd/workflows/a2-multi-env.yml`、`../examples/08-cicd/workflows/a1-cnb.sample.yml`

## 剧情回顾

- **第 1 格**：周五深夜，小研手工 `scp` 部署手一抖传错文件，线上直接炸了；想回滚？制品根本没留档。码叔定论：手工发布等于每次都在赌，重复的事交给人肉，事故只是时间问题。
- **第 2 格**：码叔亮出五站流水线——push 代码 → 门禁（lint/test/typecheck）→ 构建 → 制品入库 → 自动部署，任一站红灯立即拦截，且每站都有日志可查。
- **第 3 格**：像素贾对比两种发布策略：蓝绿是两套环境路由一键整体切换、秒级回滚；金丝雀按 1% → 10% → 100% 逐步放量，出问题只炸 1% 的用户。
- **第 4 格**：结案两个高频坑：金丝雀不等于蓝绿；回滚快不快全看制品有没有版本化。码叔总结：让机器做重复的事，让人做审查的事。

## 知识点拆解

### 第 1 格 · 手工发布为什么必然出事

- CI（持续集成）：频繁向主干合入小批量代码，每次合入自动构建 + 测试，尽早暴露冲突与回归；
- 持续交付（Continuous Delivery）：产物始终"随时可发布"，最后一步生产发布保留人工确认；持续部署（Continuous Deployment）连这一步都自动化——一词之差就在审批卡点；
- 手工 `scp`/`pm2 restart` 不可复现、无日志、无制品留档，回滚只能靠记忆；
- 落地前提：小步提交、测试可信、制品唯一且不可变（build once, deploy many）。

### 第 2 格 · 五站流水线

push 一响机器接管，快速失败在前、高成本动作在后。完整写法见 `../examples/08-cicd/workflows/i1-full-ci.yml`：

```yaml
jobs:
  lint:      # 门禁站：lint / typecheck / test 无依赖，并行调度
  typecheck:
  test:      # Node 18/20/22 矩阵，fail-fast: false
    strategy:
      fail-fast: false
      matrix:
        node: [18, 20, 22]
  build:     # 构建站：前三站全绿才执行，产物上传制品库
    needs: [lint, typecheck, test]
    steps:
      - run: pnpm build
      - uses: actions/upload-artifact@v4 # 制品入库：版本化、可留档、可回滚
```

- 五站：**push 代码** → **门禁**（lint · test · typecheck，任一红灯立刻拦截、不进主干）→ **构建**（npm/pnpm run build）→ **制品入库**（版本化存储）→ **自动部署**（蓝绿 / 金丝雀）；
- 任一站失败立即终止整条流水线，把问题挡在最便宜的阶段；每一站都有日志，顺着链路即可定位。

### 第 3 格 · 两种发布策略

- **蓝绿部署**：维护两套等价环境（绿·旧版 ⇄ 蓝·新版），路由一键整体切换，验证失败把路由切回去即秒级回滚；缺点是资源双倍、共享依赖须双向兼容；
- **金丝雀灰度**：小流量先打新版本（1% → 10% → 100%），盯错误率与性能指标逐步放量，爆炸半径最小，但需要灰度规则引擎与观测体系、发布周期更长；
- 另有滚动发布：实例逐批替换，资源开销居中但新旧共存时间长、回滚较慢；
- 前端灰度的本质：内容哈希文件名让新旧 chunk 天然共存，灰度只需在网关/CDN 边缘按流量比例、Cookie 或用户 ID 分流"谁拿到新版入口 HTML"。

### 第 4 格 · 回滚的底气来自制品

- 回滚快不快，全看制品有没有按版本入库：制品不可变，回滚 = 重新部署历史制品，而不是重新构建；
- 多环境流水线（`a2-multi-env.yml`）坚持同一个制品从 dev 一路走到 prod，只换配置；打 `v*.*.*` tag 才触发生产发布；
- 前端回滚 = 切回旧版本入口/目录，旧制品至少保留一个回滚周期，且回滚本身也要流水线化，严禁再 SSH 上服务器改文件。

## 坑点清单

1. **金丝雀 ≠ 蓝绿**：金丝雀按流量比例灰度、爆炸半径小但周期长；蓝绿是整套环境一键切流、回滚最快但资源双倍，按业务容错预算选；
2. **不做制品版本化就没有秒级回滚**：手工 scp 不留档，出事只能重新构建，回滚慢且不可信；制品必须按唯一版本入库、不可变；
3. **前端发布顺序写反会出 404 窗口**：必须先上传新的哈希静态资源、再更新入口 HTML，否则新 HTML 会引用到还不存在的文件。

## 自测 3 题（含答案）

1. 持续交付和持续部署的关键差异？——**最后一步"发布到生产"是否自动化：持续交付保留人工审批卡点，持续部署验证通过后自动上线、无需人工介入**。
2. 蓝绿和金丝雀分别适合什么情况？——**蓝绿求快：整体切流、秒级回滚，代价是双倍资源；金丝雀求稳：小流量逐步放量、爆炸半径最小，适合大用户量的高风险变更**。
3. 前端为什么能做到秒级回滚？——**内容哈希文件名让新旧版本可共存，制品按版本入库并保留历史，回滚只需把入口切回旧版本目录；前提是发布时先传资源再更新 HTML**。
